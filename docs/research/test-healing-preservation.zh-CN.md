# 测试修复后是否保留业务错误检测能力

日期：2026-10-02。状态：完成控制验证与一次模型提案回放。
[English](test-healing-preservation.md)

## 问题与先行工作

UI 发生不改变业务语义的修改后，修好的测试能否在正确应用上通过，同时在
同一个新 UI 的错误应用上继续抓住原业务错误？

[Playwright Test Agents](https://playwright.dev/docs/test-agents) 的官方 healer
允许调整断言，也允许遇到损坏功能时跳过测试。这些是合法能力，不能据此
推断实际弱化频率。[SWT-Bench](https://github.com/logic-star-ai/swt-bench)
提供修复前失败、修复后通过的判定思想；已有
[healer perturbation 实验](https://github.com/voidmatcha/e2e-skills/blob/main/benchmarks/healer-perturbation-v1/README.md)
覆盖邻近合成问题。本实验不主张问题或方法的新颖性。

## 预先登记的条件与独立观察

一个合成结账规则：两个单价 1000 分的商品，加 500 分 Express 运费，再由
FLAT2 优惠券减 200 分，正确实扣为 2300 分。故意引入的应用缺陷忽略优惠券，
实际提交扣费 2500 分。旧/新 UI 的标签与业务规则相同，DOM ID 改变。
服务器内存中的已提交扣费独立于候选测试的通过/失败结果。

控制条件是正确/错误应用 × 旧/新 UI × 原测试/强修复/弱修复，每格三次。
强修复使用可访问性定位并保留金额断言；弱修复仅检查成功提示。跳过独立
记录，定位失败不算抓住业务 bug。浏览器、观测器或外层验证失败计为无法
判定。外层 Playwright 通过只表示测量验证符合预期。

验收：强修复在正确应用通过、错误应用因金额失败；弱修复在错误应用出现
实扣 2500 分但测试通过；原选择器在新 UI 下无法操作，归类定位失败。

## 实测结果

控制矩阵完成 36 次执行：15 次正确通过、9 次抓住业务错误、6 次假通过、
6 次定位失败；另有 12 次跳过。新 UI 的强修复在正确/错误条件分别为 3 次
通过、3 次抓住错误；弱修复在错误条件的三次均假通过。

本机已登录的 Codex CLI 0.159.2 实际调用一次，输入原测试、定位超时和当前
HTML，不提供应用源码或后续错误条件结果。模型未调用工具，返回了保留金额
断言的定位修复提案。审查后仅解码字面换行并由 Biome 格式化，再在新 UI
正确/错误条件各执行三次：分别 3 次通过、3 次抓住业务错误。

这属于真实模型提案回放；官方 Playwright healer 的浏览器工具循环尚未执行，
也没有完成同模型、同工具、同预算的两套 harness 对比。记录配置请求了
gpt-6.1-sol / ultra，但返回事件没有提供实际服务模型和推理档位，所以配置
不能被写成实际生效证明。调用报告 20,054 输入 token、427 输出 token，其中
221 reasoning token。未新增服务付费，消耗了现有 Codex 额度。

两次开发控制运行已排除：第一次暴露 fixture 的可访问性命名歧义，第二次
暴露错误字符串中的 ANSI 控制码影响断言。修正后才生成正式控制记录。
原始文件、排除理由保留在本机审计目录。没有丢弃失败模型输出或发起第二次
调用修正结果。

## 结论与下一门槛

当前证明观测器能识别这个案例中的业务检测能力丢失，并记录了一个实际保留
该能力的模型提案。一次简单 ID 变化和同一业务的重复不支持推断模型可靠性、
真实 healer 弱化频率或新的研究贡献。后续先定义独立业务规则，再按相同
工具、预算比较；六案例、十八会话的方案仍未执行。
